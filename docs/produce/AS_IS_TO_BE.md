## 活動の位置づけ

本PJはTubeClipの活動の一部として、個人で進めている。ここで得た研究・探究・具体的な作業の成果は、TubeClipの活動に還元する。

## As-Is（現状）

- 魔女IPの忠実クローン。vendorの`bundle.js`をそのまま使い、外部に依存しない形で自社ホスティングしている（内製化レベル1）
- 広告と、ドコモのポイント経済圏に由来するUIは除去済み。モバイルでの操作性も調整済み
- Cloudflare Workers単体での配信基盤ができている（`npm run deploy` / `deploy:domain`）
- ゲーム単体で収益を得る仕組みは**ない**。パブリッシュ基盤（ストア配信・課金・広告SDKなど）も**ない**
- 独自IPへの差し替え（ミツモリ村）は、**成功の定義を置かずに始めたため評価できず**、ロールバックした。試行そのものは、IPは簡単には作れないと分かったという意味で、PoCとして成功している
- クリーンルームでのエンジン再実装（内製化レベル2）は途中まで。ゲーム性の再現度が不十分なままロールバックした（タグ`archive/mitsumori-ip-poc`に保存）
- **権利上の置換はまだ手つかず。** 画像・音・ロゴ・キャラクターはすべてvendorの資産のまま。さらに、どこからも使われていない他社アセット（他のゲーム24本分のサムネイルなど）が`public/images/`に残っている（詳細は[GAME_OVERVIEW.md](GAME_OVERVIEW.md#d-使っていないのに公開されてしまうものすぐ対処すべき)）

## 意義の整理（なぜやる価値があるか）

1. **パズルゲームは、ゲームを趣味としない層にも受け入れられやすい。** 1回のプレイが短く、中断や再開がしやすい。覚えることが少なく、毎日遊ぶ習慣とも相性が良い
2. **開発コストを相対的に下げられる。** 従来のゲーム開発では、ゲームデザインとバランス調整に最も時間がかかる。ほぼ完成した競合のゲームを土台にできれば、その大部分を省ける。ただし「すぐ・安く作れる」わけではない。エンジンにはロジックとコンテンツが一体で入っているため、権利上の置換とエンジンの内製化は、実際には手間のかかる作業になる
3. **1本のゲームの価値だけでなく、手順そのものが資産になる。** 「調査→内製化→広告除去→単体デプロイ」という手順は、他のタイトルにも応用できる可能性がある
4. **技術的なワークフローの実証になる。** AIエージェントで複製・内製化・再構築を進められることが分かり、TubeClipに還元できるナレッジになる

## 市場性の論拠（パズルゲームの需要は続くか）

数値の詳細は[MARKET_DATA.md](MARKET_DATA.md)にまとめた。

- **市場規模は小さくない。** 2025年のモバイルのパズルジャンルの売上は約82億ドル。Royal Match（14億ドル超）とCandy Crush（11億ドル超）は、モバイルゲーム全体でも上位に入る。当初の「アクションやRPGより市場は小さいかもしれない」という前提は修正する。ただし、売上は上位の数本に極端に集中している
- **日本でも最も遊ばれているジャンル。** スマホゲームのプレイヤーの25%がパズルをよく遊ぶと答えていて、ジャンル別で1位。女性は全年代でツムツムが1位だった
- **需要は持続する。** ぷよぷよとテトリスは今も現役で、eスポーツにもなっている。スイカゲームは、デジタルコンテンツがあふれた今でも流行した。パズルのUXが他のコンテンツに取って代わられる性質のものなら、とっくに消えているはず
- **需要の源泉はルールのシンプルさ。** 忙しい生活の中の短い時間に応えつつ、シンプルだからこそ深く遊び込める。一般層からコアなファンまで、裾野が広い
- **ペルソナは「35歳以上を中心とした女性の一般層」。** Candy Crushのプレイヤーの54〜62%は女性で、中心層も課金の中心も35歳以上の女性。日本でも女性は全年代でパズルが最も遊ばれている
- **勝敗はゲームロジックの外側で決まる。** ゲームロジックはどのタイトルもほぼ同じ。実際、後発のRoyal Matchが王者Candy Crushを逆転したとき、ダウンロードの61.5%は有料広告経由だった。勝負を分けたのはデジタルマーケティングと運営の完成度。日本では、強いIP（ディズニーなど）の影響も大きい

## ビジネスモデルの方針

- ポイント広場のような、ポータルにゲームを提供するモデルは、現実的ではないので対象外にする
- 本格的に収益化するなら、**iOS版に移植し、広告か課金要素で稼ぐ**のが現実的。選択肢は次の2つ
  - **広告型**：海外のパブリッシャーに多いタイプで、参入しやすい
  - **独自IP＋課金型**：ファンを増やしやすい
- どちらにするかは、商用化の段階で改めて決める。自社HPで公開する段階では、特に重要ではない

### 収益化の方針（[SUCCESS_DEFINITION.md](SUCCESS_DEFINITION.md)）

- **1本目の必達目標は、固定費の回収（月約7ドル）。** 成功は月200ドル、大成功は月1,000ドル。試算では、固定費の回収は数DAUから20DAU程度で届き、月200ドルには70〜560DAUが要る
- **パブリッシャー向けのポートフォリオにする案は、達成シナリオの1つ。** 普通は、自分で出して自分で進めていくのが基本になる。この道を選ぶ場合、パブリッシャーが見るのはD1リテンションとCPIという計測値で、第三者の素材やコードを含まないことが前提になる
- **当面の目標は、令和9年6月末までのL0（固定費の回収）の達成。** 手段として、Next.jsに特化した自社HP向けのWeb版を先に出す。コストが低く、責任をHPのプロジェクトに切り出すこともできるため、安全に進められる。iOS版はReact Native（Expo）で、別のプロジェクトとして再スタートし、あとでリファクタリングで統合する。「2つの選択肢があればReact Native寄りにする」以上の一般化はしない。確保できる時間は週8時間（仮値。進捗で変わる）、令和9年の予算は1.5万円。見積もりは従来型の作業を前提にした指標の一つで、「厳しい」という評価はそのまま受け止めた上で、ゆったりトライする。このプロジェクトの重心は、初期のデプロイとその安定化にあり、7月以降は、主に保守とサポートの安定化を予定する（様子を見て変わる可能性がある）（[計画と現実性の評価](L0_PLAN.md)）
- **努力は、成長の曲線に合わせて配分する。** 敷居を越えるまでかなり頑張り（A）、目標に届くまでひたすら頑張り（B）、届いた後は安定させることに力を注ぐ（C）。頭打ち（D）はほぼ到達しないものとして扱い、サポート体制の質が大きく変わる見込みが見えた時点で、プロジェクトの定義と意義そのものを再整理する（[図と方針](SUCCESS_DEFINITION.md#努力の配分方針曲線のどこで何を頑張るか)）
- **ゲーム作りとパブリッシャー機能（広告・獲得・運営）は、意識的に別の領域として扱う。** 現時点の作業は、どちらかといえばパブリッシャー的な観点からの分析。実装でも、ゲームは「広告を出してほしい」と要求するだけにして、境界を保つ
- **テーマは、中立を目指さず、軽いものを持たせる。** 作り込みの上限は1ページのテーマシートまでとし、IPバイブルは作らない

## To-Be（今回のスコープでの結論）

**本題は「ゲーム単体での収益化」。自社HPでの公開は、その仮説を低コストで試すための手段の1つであり、目的そのものではない。**

- ゲームロジックの外側の難しい部分（デジタルマーケティング、IP・キャラクター・効果音、ログインボーナスのような継続の仕組み）は、商用展開では細かく作り込む必要がある。ただ、自社HPで公開する段階では、成果の上限が「自社に興味を持ってもらう」ことなので、そこまで作り込まなくていい
- そのため今は、これらを仮の素材や既存の仕組みの流用でシンプルに済ませ、**無料での公開を優先する**
- ただし、**権利上の置換は、自社HPで公開する前提としても外せない**。置換後に何を使うかは、戦略（成功の定義、テーマの方針）が固まってから決める。先に決めると手戻りになりやすいため
- 素材を替えても、`bundle.js`はvendorのプログラムのまま。公開やパブリッシャーへの提示には、自前のエンジンが要る
- 一般公開・商用化に進むときには、後回しにした部分を作り込む作業が中心になる
- ランニングコストはほぼかからない（ドメインは自社HPのものを使い、配信はCloudflare Workersでほぼ無料）。この低コストな構造が、まず動くことの裏付けになる

## 妥協点リスト（次フェーズへの申し送り）

自社HPで公開する段階では作り込まなくていい、という前提で、仮の素材や流用で済ませている部分。一般公開・商用化に進むときに作り込みが必要になる候補として残しておく。

| 妥協した部分 | 現状 | 一般化するときに必要なこと |
|---|---|---|
| 権利上の置換 | 手つかず。vendorの資産とプログラムのまま | 置換対象は[GAME_OVERVIEW.md](GAME_OVERVIEW.md)で特定済み。置換後の素材は、IP方針が決まってから決める。エンジン（`bundle.js`）の内製化も必要 |
| IP・世界観 | 魔女IPをそのまま使っている（独自IP化は失敗してロールバック済み） | 企画の全体像とプロデュースの観点から設計し直す（[アーカイブ参照](../archive/2026-09-mitsumori-ip-poc/README.md)）。日本ではIPの有無が継続率を左右する可能性がある |
| イラスト・効果音 | vendorの資産をそのまま使っている | 魅力的なキャラクターと効果音を作り込む（権利上の置換と同時に進める） |
| ログインボーナス・毎日遊ぶ動機 | 未実装（関連するUIごと削除済み） | 継続率を支える主要な仕組み。ゲームロジックで差がつかない分、ここが差別化の主戦場になる |
| デジタルマーケティング | 未着手 | UXで差がつきにくいパズルでは、勝敗を分ける中心的な要素になる（Royal Matchの例） |
| 収益化の導線 | ない（広告も課金もない） | iOSへの移植を前提に、広告型か「独自IP＋課金型」かを選ぶ |
| パブリッシュ基盤 | Cloudflare Workers単体での配信のみ | ストア配信、アカウントの仕組み、分析基盤などは未検討 |

## 次フェーズへの引き継ぎ事項

- **すぐ対処できること**：`public/images/`に残っている、使われていない他社アセットの削除
- 権利者を特定し、公開範囲（ゲームのルール自体はどこまで使えるか）について専門家に確認する
- 自社HPに掲載するページと、そこへの導線を設計する
- 同じような案件の獲得も狙うなら、ポートフォリオとしての見せ方（Before/After、技術的な見どころ）を整理する
- 商用化に本格的に進む場合は、上の妥協点リストがそのままスコープの候補になる
- サポート体制の質が大きく変わる見込みが見えてきたら、プロジェクトの定義と意義そのものを再整理する
