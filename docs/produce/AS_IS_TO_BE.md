# magic-slide — As-Is / To-Be（プロデュース観点）

2026-09時点の整理。[docs/archive/2026-09-mitsumori-ip-poc/](../archive/2026-09-mitsumori-ip-poc/README.md)（前フェーズの反省）を受けた再スタート。

## As-Is（現状）

- 魔女IPの忠実クローンを内製化（vendor bundle.jsをそのまま使用、ゼロ外部依存で自社ホスティング）
- 広告・docomoポイント経済圏由来のUIを除去し、モバイルUXを調整済み
- Cloudflare Workers単体での配信基盤を確立（`npm run deploy` / `deploy:domain`）
- ゲーム単体でのマネタイズ手段は**ゼロ**。パブリッシュ基盤（ストア審査・課金・広告SDK等）も**ゼロ**
- 独自IPへの再テーマ化トライは失敗し、ロールバック済み（→ IPプロデュースは別スキルという学び）

## 意義の整理（なぜやる価値があるか）

1. **パズルゲームは非コアゲーマー層への親和性が高い** — セッションが短く中断・再開しやすい、学習コストが低い、デイリー動機付けと相性が良い
2. **AIによる解析で開発コストが劇的に下がる** — ゲームデザイン・バランス調整という最も時間のかかる工程を、既存タイトルの解析でスキップできる（実証済み）
3. **1本の価値ではなくパイプラインとしての価値** — 「調査→内製化→広告除去→単体デプロイ」の型は他タイトルにも横展開できる可能性
4. **技術ワークフローの実証** — AIエージェントでの複製〜内製化〜再構築が現実的に機能するという社内ナレッジ資産になる

## To-Be（今回のスコープでの結論）

**マネタイズの論理を「ゲーム単体で稼ぐ」から「自社HPのポートフォリオとして実績化し、同種案件の獲得に繋げる」に切り替える。**

- まず無料公開を急ぐ。自社サイトなので「それ自体で売れる」ことを目指さなくてよく、素早く動ける
- 難所（IP・イラスト・効果音・ログインボーナスのような企画体系、マーケティング設計）は**プレースホルダー、または既存の仕組みの流用**で一旦当てはめる
- ゲーム自体の本格マネタイズ・独自IP開発は、無料公開を起点にして**後続フェーズで本格化**する

## 妥協点リスト（次フェーズへの申し送り）

今回「急ぐために」プレースホルダー/流用で済ませた箇所。次フェーズで手を入れる候補として明示しておく。

| 妥協した部分 | 現状 | 次フェーズで検討すべきこと |
|---|---|---|
| IP・世界観 | 魔女IPをそのまま流用（独自IP化は前フェーズで失敗しロールバック済み） | 独自IPをやるなら企画体系＋プロデュース観点からの再設計が必要（[archive参照](../archive/2026-09-mitsumori-ip-poc/README.md)） |
| イラスト・効果音 | vendor資産をそのままミラー | 権利上、社外向けに本格展開するなら差し替えが必要になる可能性 |
| ログインボーナス／デイリー動機付け | 未実装（該当UIごと削除済み） | パズルゲームの継続率を支える主要な企画要素。次フェーズの目玉候補 |
| マネタイズ導線 | ゼロ（広告もIAPも無し） | 収益化手段の選定（投げ珠、プレミアムスキン、広告あり/なし出し分け等）は後回しにした論点 |
| マーケティング設計 | 未着手 | 自社HP掲載時点では不要だが、ゲーム単体で伸ばす段階では必須 |
| パブリッシュ基盤 | 無し（Cloudflare Workers単体配信のみ） | ストア配信・アカウント基盤・分析基盤などは未検討 |

## 次フェーズ（フェーズ2）への引き継ぎ事項

- 自社HPへの掲載自体は本ドキュメントのTo-Beで完結（別途、掲載先ページ・導線の設計が必要になり次第着手）
- 「同種案件の獲得」を狙うなら、ポートフォリオとしての見せ方（Before/After、技術的な見せ場）を別途整理する必要がある
- ゲーム単体マネタイズに本格着手する場合、上記の妥協点リストがそのままフェーズ2のスコープ候補になる
