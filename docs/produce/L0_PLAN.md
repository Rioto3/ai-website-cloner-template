## 進め方の心持ち

- **この計画の見積もりは、従来型の作業を前提にした指標の一つとして扱う。** AIを使う個人としての実際の速度は、進めながら測る
- **週8時間は仮値。** 進捗によって、変わりうる
- **「厳しい」という評価は、そのまま受け止める。その上で、トライする。** 6月末は、達成を試みる目標であり、間に合わせるために急ぐことはしない
- **ゆったり進める。** 急ぎすぎると、余計な作業が増えたり、他の領域を含めた判断に取り込まれたりする。ゆったり進めることで、意義がより強固になる、という評価（一つの評価）

### 「React Native寄り」の具体的な指針

一般化はしない。選択に迷ったときの、最小限の決まりだけを置く。

1. **ゲームのルール、状態、スコア、乱数、演出の順序は、DOMにもNext.jsにも依存しない純粋なTypeScriptに置く。** アーカイブのエンジンの延長にする
2. **保存、音、広告は、窓口（インターフェース）越しに使う。** ゲームの中から、`localStorage`やWebAudioを直接呼ばない
3. **素材は、両方で使える形式にする。** 画像はPNGかSVG、音は音声ファイル
4. **描画の層は薄くする。** 計算をゲーム側に置き、描画は結果を映すだけにする

## L0の定義

| 段階 | 内容 | 扱い |
|---|---|---|
| **L0-a：収益が立つ** | **発生主義で**、AdMobの推定収益が月約7ドル（約1,070円）相当になる。判定の月は6月とする | **目標にする** |
| **L0-b：現金で回収する** | 年会費相当が入金される | 支払い元の事情として整理する。目標にしない |

L0-bが遅れるのは、**支払い元（AdMob）の支払い基準額**のため。日本円のアカウントでは8,000円（米ドルは100ドル）で、確定額で判定される。L0水準の月約1,070円のペースでは、初回の入金まで約7〜8か月かかる。会計上は収益が立っているので、L0-aの達成は妨げない。推定収益は、あとで確定額との差を確認する。

## 作業量と、週8時間（312時間）との照合

**私の見積もりで、データに基づく数字ではない。** 実際の作業速度、特にAIの活用による圧縮の度合いで、大きく変わる。

**スコープの前提：** コア（盤面、スライド、重力、消去、せり上がり、スコア、ゲームオーバー、再挑戦、ベストスコアの保存）と、広告を出す窓口（リワード広告での続行）、テーマ素材、音。**ブースター、ショップ、ガチャ、コイン、壺とダイヤは作らない。**

### Web版（Next.js、自社HP向け）

### iOS版（React Native、別のプロジェクト）

## 現実性の評価

**「厳しい。何か手を打たないと、中央値では6月下旬の公開になり、L0-aの判定月に間に合わない」。**

| 項目 | 評価 | 根拠 |
|---|---|---|
| Web版を公開する（1月〜2月上旬） | **現実的** | エンジンと試作がすでにある。Web版だけなら、約100〜165時間 |
| iOS版を5月中旬までに公開する | **厳しい** | 中央値の310時間だと、6月下旬になる。下限（230時間）でも4月中旬 |
| 6月にL0-aを達成する | **iOS版が5月中旬までに公開できれば、見込みあり** | 必要なDAUは3〜20人程度と、低い水準。ただし、流入がゼロになる可能性は残る |

**この評価は、そのまま受け止める。その上で、トライとして進める。**

**Web版を先行し、iOS版を別のプロジェクトにする決定は、自社HPへのデプロイを安全に先行できる、という意義がある。** その代わりに、iOS版の作業が約40〜60時間増える。その差を、次のような手で埋める必要がある。

## 対応案

**現時点では、どれも取らない。** 進捗を見て、必要になれば検討する。

| 手 | 効果 |
|---|---|
| 2〜5月だけ、週8時間を10時間にする | 約34時間分。公開が約4週早まる |
| スコープをさらに絞る（BGMなし、ポリシーと計測を最小に、素材を最小のセットに） | 15〜20時間分 |
| 判定の月を7月にする（期限を7月末に延ばす） | 公開の最終期限が、6月中旬になる（約4週の延長） |
| 「React Native寄り」の指針を徹底する | iOSの描画と操作の再実装が、見積もりの下限に近づく可能性がある |

**上の最初の2つを合わせると、中央値が、ちょうど最終期限に収まる。** 判定の月を延ばす手は、期限を変える手なので、最後に取る。

## リスク

| リスク | 内容 | 対策 |
|---|---|---|
| **スケジュール** | 中央値で、最終期限に間に合わない | 対応案から、2つ程度を取る。ゲート2で見積もりを再判定する |
| **React Nativeの検証が遅れる** | 検証はiOS版の開始（2月）になるので、失敗に気づくのが遅れる | iOS版の開始時のスパイクで確認する。失敗した場合は、Web版をWebViewで包む案に切り替える |
| **審査（4.3など）** | 他のアプリに酷似したアプリや、飽和したカテゴリのアプリは、スパムとして却下されることがある。プライバシーの申告と実際の挙動が食い違っても却下される。審査は、90%以上が48時間以内に結果が出るとされる | テーマ・演出・手触りで差を出す。リジェクトが1回あっても間に合う余裕を持つ。プライバシーの申告は、広告SDKの実際の挙動と合わせる |
| **権利** | 素材とエンジンの置換が終わっていることが、HPの公開とiOSの公開の、どちらの条件にもなる | 公開前に、専門家への確認を入れる |
| **流入** | 公開しても、誰にも見つけてもらえない可能性がある | 自社HPからの導線、ストア検索のキーワード、30秒の動画を、公開前から準備する |
| **新規アプリの広告** | 新しいアプリは、公開直後に広告の配信が安定しないことがある | 判定の月の2週間前までに公開する |
